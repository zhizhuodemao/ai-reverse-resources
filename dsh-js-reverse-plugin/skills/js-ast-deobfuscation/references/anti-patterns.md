# JavaScript 解混淆反例

本 reference 用于设计检查、风险升级和前向测试。每条都使用同一结构：

- **错误做法**：容易出现的错误。
- **为什么错**：它破坏了哪条证据或交互边界。
- **正确分流**：遇到时应该怎样处理。

## 1. 分析反例

### 1.1 跳过 Prettier

- **错误做法**：直接在压缩原文上建立完整画像。
- **为什么错**：模型难以完成连续、可复核的全文件阅读，源码锚点也不稳定。
- **正确分流**：冻结原始输入，只对派生副本使用本地 Node Prettier；格式化成功后再画像。

### 1.2 原地格式化

- **错误做法**：在原始目标上运行 Prettier。
- **为什么错**：破坏原始 hash、运行证据和 self-defending 对照。
- **正确分流**：保留固定 hash 原件，把格式化结果写入独立分析副本。

### 1.3 静默更换 formatter

- **错误做法**：本地没有 Prettier 时改用其他打印器，或者让 AST generator 冒充准备步骤。
- **为什么错**：违反固定准备契约，输出不可比较，也掩盖真实解析问题。
- **正确分流**：在隔离工作区本地安装 Prettier；安装或解析失败时进入 `FORMAT_BLOCKED`。

### 1.4 只让脚本看代码

- **错误做法**：只读取 AST 统计、正则结果或自动分类摘要，模型不直接阅读完整格式化源码。
- **为什么错**：脚本只能回答预先编码的问题，会遗漏新结构并放大预设立场。
- **正确分流**：模型按连续区间直接阅读全文件，再用脚本复核数量和定位遗漏。

### 1.5 抽样冒充全量

- **错误做法**：只看开头、中段和结尾，却声称已经识别全部当前可见模式。
- **为什么错**：大文件中的载荷、入口和消费者可能集中在未读区间。
- **正确分流**：记录已读区间并分块继续；未覆盖完整文件时保持 G3 进行中，不提交画像、不进入语义步骤，也不把部分读取包装成“下界画像”。

### 1.6 混淆家族数与出现次数

- **错误做法**：用一个数字同时表示“有几种混淆”和“匹配了多少节点”。
- **为什么错**：结构复杂度和影响规模是不同概念。
- **正确分流**：分别记录家族数、每类出现次数和影响范围，并定义计数单位。

### 1.7 把首轮画像当最终全集

- **错误做法**：初次扫描后宣称不会再出现新模式。
- **为什么错**：字符串恢复和载荷解包经常暴露新的代码层。
- **正确分流**：称为“当前视图中可见的模式”，每个通过步骤后重新画像。

### 1.8 根据背景预判

- **错误做法**：根据文件名、站点、课程主题或历史案例直接套结论。
- **为什么错**：相同来源也可能更换构建器、版本、入口和混淆器。
- **正确分流**：先读真实片段和消费者，再用案例作为比较材料，不把案例当证据。

### 1.9 看到 Base64 就宣布字符串池

- **错误做法**：只凭 Base64 外观认定它是字符串混淆。
- **为什么错**：它也可能是图片、证书、压缩资源、协议数据或 VM 记录。
- **正确分流**：读取生产链、解码链和消费者；无法确认时标为 `Unknown`。

### 1.10 看到 switch 就宣布控制流平坦化

- **错误做法**：把每个大型 `switch` 都归类为 dispatcher。
- **为什么错**：状态机、协议解析器、编译器和 VM 解释器都有相同表面形态。
- **正确分流**：检查状态来源、更新、case 终止和代码角色；VM dispatcher 交接 VM 阶段。

### 1.11 看到数字模块 ID 就猜业务名称

- **错误做法**：凭模块序号或少量字面量直接命名。
- **为什么错**：数字 ID 是打包器常见基础设施，猜名会污染后续分析。
- **正确分流**：先识别模块表、缓存、加载器和依赖图；证据不足时保留 ID 或使用中性名。

### 1.12 识别第三方后直接删除

- **错误做法**：确认是 polyfill 或第三方库后将其移除。
- **为什么错**：来源分类不证明无引用、无副作用或不参与入口初始化。
- **正确分流**：默认保留；与目标无关时跳过内部清理，需要删除时升级询问并检查引用。

### 1.13 把静态存在当运行事实

- **错误做法**：看到字符串、模块、分支、slot 或 API，就说它进入最终输出。
- **为什么错**：静态存在、可达和已观察执行是三个不同结论。
- **正确分流**：分别记录 `Observed / Inferred / Unknown`；需要运行事实时提出最小证据缺口。

## 2. Transform 反例

### 2.1 按文本全局替换

- **错误做法**：用字符串替换所有同名标识符。
- **为什么错**：不同作用域中相同文本可能解析到不同 binding，属性文本也不是局部变量。
- **正确分流**：只基于词法 binding、声明和引用进行修改；无法解析的目标保持不变。

### 2.2 不解析 shadow 就重命名

- **错误做法**：只定位一个声明，不检查内外层 shadow 和新名称冲突。
- **为什么错**：会改变解析关系或制造捕获。
- **正确分流**：检查可见 binding、全部引用和 shadow；多个语义解释成立时使用中性名或询问。

### 2.3 一步混合多个 transform 家族

- **错误做法**：一次同时恢复字符串、内联代理、删除死代码并语义重命名。
- **为什么错**：失败时无法定位原因，也无法准确统计和回滚。
- **正确分流**：每步只处理一种边界明确的结构，分别生成输入、输出和报告。

### 2.4 为提高命中数扩大匹配

- **错误做法**：遇到不符合前提的节点时放宽条件，让 transform 尽量多改。
- **为什么错**：命中率上升不等于正确率上升，容易跨越语义边界。
- **正确分流**：超出前提的节点跳过或令本步停止，把残留写入下一候选。

### 2.5 删除前不检查副作用

- **错误做法**：看到未使用声明、恒假分支或反调试信号就删除。
- **为什么错**：初始化、getter、异常、全局写入和遥测可能仍有行为。
- **正确分流**：检查引用、别名、动态属性和副作用；删除属于需要明确授权的高风险步骤。

### 2.6 把快照 alias 当永久恒等

- **错误做法**：把一次 `alias = source` 推广为所有位置的双向等价。
- **为什么错**：后续重新赋值或对象替换会使关系失效。
- **正确分流**：限定赋值时点和控制流范围；证据不足时只记录潜在连接。

### 2.7 用高语义名称填补未知

- **错误做法**：根据直觉把短名改成具体业务含义。
- **为什么错**：名称会把假设伪装成事实，并影响后续推理。
- **正确分流**：使用 loader、entry、slot、record 等中性角色名；业务名称必须询问或有更强证据。

### 2.8 没有映射和残留就宣布成功

- **错误做法**：只展示几段变得可读的代码。
- **为什么错**：无法知道实际修改、跳过和未覆盖范围，也无法回到原始位置。
- **正确分流**：保存输入输出、修改范围、跳过、残留和原始到派生映射；验收交给 validation reference。

## 3. 交互反例

### 3.1 把“解混淆”当信息不足

- **错误做法**：要求用户先说出混淆类型、技术路线和最终产物。
- **为什么错**：用户使用 Skill 正是因为不知道这些技术事实。
- **正确分流**：自动冻结、格式化、直接阅读和画像；看到源码后再让用户反馈分析方向。

### 3.2 首轮画像前询问最终用途

- **错误做法**：读代码前问用户要 static 还是 dynamic、是否进入 VM、最终解到哪一层。
- **为什么错**：用户没有源码画像就无法做有信息的选择。
- **正确分流**：先提交模式、依赖、收益和风险，再用普通语言提供选择。

### 3.3 模型自动解到底

- **错误做法**：模型自行决定并连续执行所有语义步骤。
- **为什么错**：不同步骤的风险、成本和阶段边界不同，用户失去决策权。
- **正确分流**：默认 `interactive`，每次只提交一个推荐步骤和真正不同的替代项。

### 3.4 一个批准覆盖后续全部步骤

- **错误做法**：用户同意字符串恢复后，自动继续控制流、删除和命名。
- **为什么错**：一个步骤的授权不能扩展到新的风险和语义范围。
- **正确分流**：批准默认只覆盖当前步骤；批次或 autonomous 必须由用户明确授权。

### 3.5 只问“是否继续”

- **错误做法**：不给候选、收益、风险和不处理的影响。
- **为什么错**：用户只能盲目同意或拒绝。
- **正确分流**：提供推荐、替代、暂停或交接选项，并解释各自能得到什么。

### 3.6 要求用户替模型选择技术模式

- **错误做法**：要求用户决定 static、hybrid、binding-aware rename 或 dispatcher unfold。
- **为什么错**：这些是模型应根据证据完成的技术判断。
- **正确分流**：模型先确定方法，用普通语言向用户说明结果、风险和范围。

### 3.7 用户未回应仍继续

- **错误做法**：决策卡发出后默认用户同意。
- **为什么错**：沉默不是授权，尤其不能授权动态执行、删除或阶段切换。
- **正确分流**：进入 `READY_FOR_USER_DECISION` 并保留当前工作区。

## 4. 动态反例

### 4.1 因为有运行环境就默认动态

- **错误做法**：iv8、浏览器或调试器已经可用，所以先执行目标。
- **为什么错**：工具可用性不能代替证据需求，动态覆盖还可能更窄。
- **正确分流**：先明确当前问题和静态缺口；静态足够时不执行。

### 4.2 静态步骤中途静默升级

- **错误做法**：用户只批准静态 transform，模型发现困难后直接运行目标。
- **为什么错**：动态执行改变风险、权限和证据边界。
- **正确分流**：停止本步，保留上一个通过版本，提交最小动态取证方案并重新请求批准。

### 4.3 为局部 decoder 执行完整未知目标

- **错误做法**：为了取得一个确定性解码结果，加载整个文件、页面或网络流程。
- **为什么错**：扩大副作用和环境变量，降低证据可解释性。
- **正确分流**：优先隔离闭合 decoder；无法隔离时再说明具体依赖和升级理由。

### 4.4 在原始 JS 中插日志

- **错误做法**：直接加入 `console.log`、`debugger` 或 collector 调用。
- **为什么错**：改变原始 hash、源码完整性、时间行为和运行证据。
- **正确分流**：先使用引擎日志、外部断点和宿主旁路；最后才对独立派生副本插桩。

### 4.5 把源文件零修改称为绝对无侵入

- **错误做法**：runtime Hook 没改磁盘文件，就宣称运行完全不受影响。
- **为什么错**：Hook、断点、debug 模式和日志都可能改变对象可观察性或时序。
- **正确分流**：区分“源文件零修改”和“运行时零影响”；Hook 明确标记 `runtime patched`。

### 4.6 Hook 后没有 A/B

- **错误做法**：安装 probe 后只运行一次并直接采用结论。
- **为什么错**：无法判断结果来自目标本身还是 probe。
- **正确分流**：保存无 probe 基线和有 probe 结果，使用相同输入、环境和触发做 A/B。

### 4.7 因为已安装 iv8 就使用 iv8

- **错误做法**：一个纯静态或闭合局部问题也启动完整浏览器语义。
- **为什么错**：增加环境差异、成本和证据噪声。
- **正确分流**：只有问题依赖宿主 API、页面生命周期、事件循环等能力时才选择 iv8。

### 4.8 异步值尚未稳定就读取

- **错误做法**：触发异步入口后立即读取结果。
- **为什么错**：任务队列、计时器、Promise 或事件尚未完成，空值不代表没有行为。
- **正确分流**：按运行时语义推进或排空事件循环，并记录推进方式和覆盖窗口。

### 4.9 把 `node:vm` 当安全沙箱

- **错误做法**：使用 `node:vm` 执行不可信目标并称为安全隔离。
- **为什么错**：它不是不可信代码的安全边界。
- **正确分流**：缩小执行范围、限制权限；完整未知目标执行必须单独授权和采用真正隔离。

### 4.10 执行派生视图冒充原始行为

- **错误做法**：运行格式化、重命名或插桩后的文件，并把输出当作原始目标证据。
- **为什么错**：分析视图不默认承诺行为等价。
- **正确分流**：行为证据优先运行固定 hash 原件；派生执行结果明确降低证据等级。

### 4.11 把属性访问写成算法依赖

- **错误做法**：日志显示读取某 API，就说它进入最终签名或业务输出。
- **为什么错**：读取可能只是探测、缓存、无效分支或遥测。
- **正确分流**：记录“已观察访问”；要证明输出依赖，需要新的数据流或对照证据。

### 4.12 不记录运行条件

- **错误做法**：只保存最终值，不记录输入、环境、时间、随机数、补丁、trigger 和覆盖路径。
- **为什么错**：结果不可复现，也无法限定适用范围。
- **正确分流**：保存执行目标 hash、配置、输入、环境状态、原始日志和未覆盖范围。

### 4.13 把一次运行推广到所有路径

- **错误做法**：一次动态观测后做全局替换或删除所有未执行分支。
- **为什么错**：动态证据只覆盖特定输入、环境和路径。
- **正确分流**：将运行值映射到对应调用点；全局结论需要额外静态证明或多组覆盖。

### 4.14 把完整补环境塞进 AST Skill

- **错误做法**：为推进一个候选，在 AST reference 中复制完整环境、网络桥接、指纹和服务器验收流程。
- **为什么错**：扩张了 Skill 边界并制造对特定框架的隐式依赖。
- **正确分流**：本 Skill 只定义最小动态证据；系统补环境交接专门的运行环境阶段。

### 4.15 在 AST Skill 中插桩 VM 内部

- **错误做法**：记录 Opcode、PC、值栈、帧栈或虚拟函数轨迹。
- **为什么错**：这已经进入 VM 逆向，不再是外围 AST 解混淆。
- **正确分流**：只建立 VM 入口、数据区、宿主 binding 和公开 API 坐标，然后交接 VM Skill。

## 5. 完成度与阶段边界反例

### 5.1 语法通过就宣布完成

- **错误做法**：`node --check` 或重新 parse 成功后结束。
- **为什么错**：语法正确不证明 binding、结构、证据和分析目标正确。
- **正确分流**：按产物类型执行对应验收，再评估当前问题是否已经解决。

### 5.2 因为还有第三方短名就拒绝结束

- **错误做法**：必须清理所有 polyfill 和依赖内部变量。
- **为什么错**：这通常只改善外观，不服务当前分析目标。
- **正确分流**：记录为已分类、低收益残留；不阻碍目标时默认跳过。

### 5.3 因为分析视图不可执行就继续补

- **错误做法**：把 analysis-js 修成完整独立运行程序才肯结束。
- **为什么错**：分析视图的目标是可读、可搜、可定位和可映射，不默认替代原程序。
- **正确分流**：只有用户明确要求 executable-js 时才进入行为等价和运行修补。

### 5.4 因为算法尚未纯算就判定 AST 未完成

- **错误做法**：必须恢复最终公式或脱离所有环境，才算解混淆结束。
- **为什么错**：算法还原、补环境和 AST 解混淆是不同阶段。
- **正确分流**：外围入口、输入、输出和边界已经稳定时，可以结束 AST 阶段并交接。

### 5.5 在 AST 阶段解释 VM 语义

- **错误做法**：给 Opcode、虚拟栈和字节码使用确定业务含义。
- **为什么错**：没有 VM Trace 和虚拟控制流证据时，这些名称只是猜测。
- **正确分流**：使用 entry、slot、record 等中性坐标，把内部问题交接 VM Skill。

### 5.6 用残留数量决定结束

- **错误做法**：只要还有任何混淆候选就继续。
- **为什么错**：低收益尾部可以无限存在，残留不等于仍阻碍目标。
- **正确分流**：相对于当前分析方向、收益和阶段边界提出关闭或交接。

### 5.7 模型自行标记 COMPLETE

- **错误做法**：模型认为已经足够，就直接宣布任务全部完成。
- **为什么错**：用户可能要继续深入、换方向或转入下一阶段。
- **正确分流**：先进入 `READY_FOR_USER_CLOSURE`，提交成果、残留和交接选项；只有用户确认后标记 `COMPLETE`。
