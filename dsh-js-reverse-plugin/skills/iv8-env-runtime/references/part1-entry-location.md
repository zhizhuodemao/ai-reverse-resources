# Part1 · 入口定位：从真实出口倒推

> 本文 = P1「找入口」阶段的方法论主文档。目标：用 js-reverse MCP 在真实浏览器里，
> 从「删了就挂」的真实出口一路倒推，定位目标字段**真实生成入口**并给它分类。
> 工具怎么点 → 见 `references/part1-mcp-tool-map.md`；端到端实例 → 见
> `references/case-intercept-douyin.md`、`references/case-function-iwencai.md`。
>
> **退出闸（CHECKPOINT）**：`assets/entry-report-template.txt` 全字段填满，且末行
> 结论写「已定位」。任一字段只有猜测/调用栈痕迹而无动态边界证据 → 结论只能写「未定位」，
> 不许进 P2。

---

## 0. 一句话心法

**入口定位不是先读懂混淆代码，而是让真实浏览器里的代码自己跑，在真实出口附近观察
参数「从无到有」的边界。** 顺着一个观察（请求里有个怪参数）一步步逼出真相，
不是预先知道答案；每一步用一个实验确认，实验说话。

---

## 1. 核心原则（四条铁律）

1. **先找真实出口，再从出口倒推 JS**。出口 = URL / header / body / cookie / storage /
   XHR.open / fetch / sendBeacon / callback / return。
2. **同一个出口里的多个新增参数，逐个确认来源**。一个 JS 可以同时「生成 A」并「搬运 B」；
   不能因为都在同一个 URL 里就默认来源相同。
3. **生成、读取、搬运、写入分开描述**。它们在调用栈里都会「出现」，但只有「生成」是入口。
4. **定位正确的核心证据是「上一层没有，下一层有」，不是「调用栈里出现过」**。
   看到某 JS 出现在栈里，只能说明它参与了流程，不能说明它生成了目标参数。

---

## 2. 七步执行流程

1. **明确目标字段**：字段名、所在请求/存储位置、真实样例值。
2. **找到真实出口**：确认字段长在 URL query / header / body / cookie / storage 的哪里
   （删掉它重放 → 被拦/空数据 ⇒ 确认它是门票，就是要逆的目标）。
3. **在出口处下断点**：优先断 XHR/fetch、cookie setter、storage setter 或目标函数返回点。
4. **从断点向上看调用栈，只给每层定角色**（见 §3 角色表），不硬读混淆代码。
5. **切到疑似 JS 的 frame，主动 evaluate**：改写前输入、改写后输出、中间结果、配置对象。
6. **对每个新增参数单独追来源**（见 §4 判定表）。
7. **做最小复现 + 对照实验**：模拟真实触发方式（而非臆造 sign 函数）；不触发没有、触发后
   出现；改输入/清空状态后结果符合预期变化。

> P1↔P2↔P3 可来回迭代：P2 起手跑发现缺 API，可能要回 P1 补看某帧；不是单向。

---

## 3. 调用栈角色表（只有「生成」= 入口）

| 角色 | 含义 | 是否等于生成入口 |
|---|---|---|
| 加载 | 加载目标 SDK 或业务包 | 否 |
| 初始化 | 传入 config，安装 hook 或启动状态机 | 不一定 |
| 触发 | 发起请求、事件、队列或异步任务 | 不一定 |
| **生成** | **现场算出目标参数值** | **是** |
| 读取 | 从 cookie/storage/内部状态/响应缓存取已有值 | 否 |
| 搬运 | 把已有值写入 URL/header/body/storage | 否 |
| 发送 | 把最终请求送到网络出口 | 否 |

调用栈只能帮助定位，不能直接等于结论。定角色时优先找「哪一帧的输入里还没有目标值、
输出里已经有了」——那一帧才是生成帧。

---

## 4. 参数来源判定表（逐参数写结论）

| 来源类型 | 判断标准 | 验证方式 |
|---|---|---|
| 本地生成 | 上一层没有该值，下一层出现该值，中间结果 == 最终出口值 | 改输入后目标值随输入变化 |
| 已有状态搬运 | 出口值 == cookie/storage/全局状态/SDK 内部状态里的已有值 | 修改或清空已有状态后，出口值同步变化或消失 |
| 服务端下发 | 出口值 == 前序响应的 header/Set-Cookie/body/重定向参数 | 清 cookie/storage/network 后重放，比对前序响应与最终出口 |
| 未确认 | 只有调用栈/变量名/猜测/代码片段，无动态边界证据 | 只能写「未定位」 |

同一出口出现多个新增参数时，为**每个参数分别写来源结论**。

---

## 5. 六大入口类型表

| 入口类型 | 判断标准 | 最小复现 |
|---|---|---|
| 函数式 | 调用函数后直接 return 目标结果 | 加载 JS → 调函数 → 读 return |
| 拦截式 | init 后 hook XHR/fetch，请求发出时改写参数 | init(config) → 触发 XHR/fetch → 从出口读结果 |
| 事件式 | 点击/输入/滑动/message 等事件后出现结果 | 准备状态 → dispatch/click/input → 读出口 |
| 状态机式 | 依赖异步任务/timer/microtask/队列推进 | 初始化 → 触发动作 → 推进队列(drain) → 读出口 |
| 采集式 | 读取环境后生成 cookie/sensor/telemetry | start/init → 触发采集 → 读 cookie/beacon/storage |
| 下发式 | 参数来自前序网络响应 | 清状态 → 重放 → 对比响应与后续出口 |

> 类型决定 P2/P3 的复现骨架：函数式 → 直接调函数（爱问财 hexin-v）；拦截式 → 装 hook +
> 触发 + 捞 netLog（抖音 a_bogus）；状态机/采集式 → 必须用 `__iv8__.eventLoop` 推进后再读，
> 见 `references/network-and-eventloop.md`。
> **本 skill 不涉及以真实鼠标轨迹/行为采集为核心的行为反爬边界与内容。**

---

## 6. 禁止结论清单（写了这些 = 未定位）

下面任一表达都不能算「已定位」：

- 可能是 / 大概是 / 应该是。
- 和某 SDK 有关。
- 调用栈里出现了某 JS。
- 变量名看起来像。
- 代码里搜到了字段名。
- 先把环境补齐后再看。
- 硬读混淆代码或 VMP 后推测。

**没有「上一层没有、下一层有」的动态边界证据时，结论只能写「未定位」。**

---

## 7. 动态边界证据要采什么

在断点处直接 evaluate，把下面这些采下来（对应 `assets/entry-report-template.txt`）：

- **上一层输入**：是否含目标字段？值是什么？
- **下一层输出**：是否含目标字段？值是什么？
- **中间结果**：哪个变量/返回值 == 最终目标字段？
- **配置对象**：当前命中了什么规则（如拦截白名单 paths）？
- **触发前状态**：JS 是否加载、init 是否完成、cookie/storage/config 是否存在。
- **主动触发方式**：调函数 / 触发 XHR/fetch / 事件 / timer / 队列 / getter。
- **输入参数**：this、arguments、URL、method、headers、body、config、事件对象。
- **输出读取位置**：从 URL/header/body/cookie/storage/netLog/return/callback 的哪里读。
- **对照实验**：不触发、触发、改输入、清状态、重放请求后的对照结果。

---

## 8. 结论输出

P1 结论必须落到 `assets/entry-report-template.txt` 的字段模板：目标字段 / 真实出口 /
直接相关 JS / 入口类型 / 来源类型 / 前置状态 / 主动触发方式 / 输入参数 /
**上一层没有的证据** / **下一层已有的证据** / **中间结果 == 最终结果的证据** /
输出读取方式 / 对照实验 / 结论(已定位|未定位)。

三条证据（上一层没有 / 下一层已有 / 中间结果==最终结果）**同时齐备**才允许写「已定位」。
齐备后进 P2（`references/part2-discovery.md`）。
